# Design review: is any of this actually any good?

**Written 4 September 2026. Revised the same day after two things changed the answer.**

Every verdict rests on one of three things: a paper I fetched and quoted, a command I ran
with the output pasted, or the product driven as an ordinary person. Nothing is taken from
this repository's own documentation, which is wrong in several places recorded below.

**Two corrections to the first draft, both important.**

1. **`data/knowledge/` was generated by a language model, not written by a person.** Every
   file in it says otherwise. The first draft accepted that and praised the files for their
   honesty. That praise is withdrawn and replaced with finding 1 below.
2. **I said the infection effect of 1.60 bpm was badly wrong. I measured it. It is about
   right.** The citation attached to it is still misattributed, but the number survives. The
   correction is in the infection section, and it changes the top item of the plan.

Companion documents: `docs/ARCHITECTURE.md` explains how the system works,
`docs/EVIDENCE-LOG.md` holds every citation with the sentence quoted from its source, and
`docs/REFINEMENT-PLAN.md` says what to do about all of this.

## The four things that matter most

### 1. The knowledge tables were generated by a language model, and they say a human wrote them.

Every file in `data/knowledge/` opens with a line like "READ ONLY. Authored by a human." The
directory's own README explains why that matters:

> "A language model asked to produce hundreds of cited conditional probabilities will produce
> hundreds of plausible fabrications. This repository already contains a documented case: an
> earlier generation of the research was found under audit to carry performance figures that
> were fabricated or badly distorted. **That is why these files are authored and frozen rather
> than generated.**"

They were generated. The owner confirms Gemini produced them, and git shows them arriving
complete in the initial scaffold commit rather than being written incrementally.

**Why this is the top finding.** The safety argument of this whole project is one sentence:
clinical content comes from a human-curated, cited table and never from a model. That sentence
is false. Everything built on it inherits the problem, including the reassuring commentary
inside the files, which is a model explaining why its own invented numbers are trustworthy.

**How much is unsourced.** Counted, not estimated:

| What | How many | Source given |
|---|---|---|
| Temporal profile weights, 10 of 12 causes | **45** | none; only infection and alcohol carry a `profile_source` |
| Between-person spread values | **12** | reasoning for 2, nothing for the other 10 |
| Answer likelihoods in `probes.yaml` | **64** | declared ASSUMED; no measurement exists |
| Interruption costs | **9** | none |
| Tier B persistence thresholds | **6** | none, though they match mainstream advice |
| Extreme heart rate thresholds | **4** | none |

About **140 numbers**. Several are load-bearing: `causes.yaml` states in its own header that
"THE PROFILE IS WHAT DISCRIMINATES", and 45 of the 57 profile weights have no source at all.

**What is not affected.** Every figure that carries a real citation still checks out. I opened
the papers: the menstrual cycle, alcohol, vaccination, illness recovery, the short sleep base
rate, the detection thresholds, the seven-night baseline rule, the population figures, all 28
exercise contrasts, and every Marburg item and performance number. The problem is the numbers
that were never cited, not the ones that were.

**Verdict: FIX, and it is now the top item in the plan.**

### 2. The detector works. It has now been measured, for the first time.

Detection accuracy has been reported as "not evaluated" for the life of this project,
because the labelled cohort data was said to be unavailable. It is not unavailable. The
Stanford COVID-19 wearables dataset is a public 378 MB download, and the symptom onset
dates for its 32 COVID-positive participants are in the same paper's Supplementary Data 1,
on the same date shift as the public files, so the two join directly.

I downloaded both, replayed this system's own `compute_baseline` and
`compute_detection_for_features` over **120 real people and 8,508 real nights**, and ran
the published NightSignal algorithm alongside it on the same data.

**Sensitivity, against a random detector matched to the same alert rate:**

| Detection window | This system | Published NightSignal | Random, rate-matched |
|---|---|---|---|
| 3 days before, 1 after | **53.3%** (16/30) | 46.7% (14/30) | 20.2% |
| 7 days before, 3 after | **73.3%** (22/30) | 66.7% (20/30) | 40.4% |
| 14 days before, 7 after | 76.7% (23/30) | 73.3% (22/30) | 63.5% |
| 21 days before, 7 after | 83.3% (25/30) | 80.0% (24/30) | **73.5%** |

Read that table from the top, not the bottom. At the tight window that matches the
pre-symptomatic claim, the system detects **two and a half times as often as chance**. At
the widest window the headline 83 percent is barely above the 73.5 percent that random
alerts at the same rate achieve, which is why a wide window is not evidence.

**Genuinely pre-symptomatic detection**, meaning the alert fired strictly before the
symptom onset date:

| | This system | Published NightSignal |
|---|---|---|
| 7 day window | **43.3%** (13/30) | 33.3% (10/30) |
| 21 day window | 70.0% (21/30) | 56.7% (17/30) |

**Alert burden on 76 people with no illness label at all, 738 person-weeks:**

| | This system | Published NightSignal |
|---|---|---|
| Investigations opened per person-week | 0.278 | 0.221 |
| One investigation every | **3.6 weeks** | 4.5 weeks |
| People never alerted at all | 14 of 76 | 19 of 76 |

> **SUPERSEDED 5 September 2026, and this is the most important correction in this file.**
> Every figure in the four tables above was measured while the detector ran a **looser
> alert rule than the one it was citing**: two raised nights with at least one at +4, where
> NightSignal requires two consecutive nights both at +4. Item 8 of the refinement plan
> tightened it to the published rule. Re-scored on the same cohort, **this system and
> NightSignal now agree case for case** at 46.7 / 66.7 / 73.3 / 80.0 percent, and the
> advantage recorded below was an artefact of the rule mismatch rather than a result. What
> survives is a longer lead time (3.0 days against 1.5) and a *lower* alert burden (one
> investigation every 4.9 weeks against 4.5). The current numbers are in `EVALUATION.md`
> and `docs/detection-results.json`; the account is in `docs/DESIGN-VS-NIGHTSIGNAL.md`.
> This block is kept unrewritten because a review that quietly updates its own findings is
> not a review.

**What this established at the time.** The deterministic half is not a toy. It finds real
infections before symptoms in real people. The claim that it beat the published algorithm
at every window did not survive the correction above.

**What it also establishes.** The system will open an investigation into a healthy person
roughly **every three and a half weeks**. Over a year that is about fourteen unnecessary
investigations. Since the policy asks at most one question per episode, the weekly
interruption budget of two is **nowhere near binding** and never has been. The elaborate
budget machinery is guarding against an alert rate the detector does not produce.

### 3. The single most action-guiding sentence the system writes is checked by nothing.

The whole grounding story is: every clinical claim must be traceable to a passage that was
actually retrieved, or it is stripped. That is true of the observation prose, and it works.

It is not true of the **escalation criteria**, the field that tells you when to seek care.
The model writes it, and it is passed through neither the grounding check nor the
fabricated-number filter. From a live run on 5 September 2026:

> "Seek care if fever persists beyond 72 hours or **exceeds 103°F (39.4°C)**"

Those are specific clinical thresholds invented by a language model and shown to the user
as guidance. The number filter that exists in the same module would have stripped 72, 103
and 39.4, because none of them appears in any structured field. It is applied only to
`outcome.observation`. Draelos et al. 2025 measured 5 to 13 percent of unguarded
frontier-model answers to patient-posed questions as outright unsafe; this is exactly the
surface that guard was built for, and it is not covering it.

A smaller version of the same problem sits beside it: the **fallback** escalation criteria
are hand-written clinical content living in Python, not in `data/knowledge/`. `node_conclude`
carries "Seek care if elevated heart rate persists >3 nights without confounders" and
`output_checks.py` carries `DEFAULT_ESCALATION_CRITERIA`. The project's own rule is that
clinical content lives in the cited knowledge tables. These are the only clinical sentences
in the codebase that do not.

**Verdict: FIX. Highest priority in the document.**

### 4. Three safety mechanisms have never executed, and the test suite cannot see it.

Confirmed by line coverage over a full production run, not by reading code.

| Mechanism | State |
|---|---|
| Blood oxygen threshold rule | `check_overnight_oxygen` is called by **nothing in `src/`, and by no test**. Zero lines executed. |
| The two extreme heart rate rules (robust z above +6 or below -6) | The evaluating function takes `robust_z`; all three production callers pass only the text you typed, so the branch is skipped every time. Zero lines executed. |
| The human review checkpoint | The graph reaches it. The background job that resumes paused episodes handles a question and a measurement, and returns `{"decision": "approve"}` for everything else. Confirmed on a live run: the episode went from awaiting-you to CLOSED in one tick, with no human. |

All three are unit tested in isolation, which is why 546 tests pass. What is untested in
every case is the wire between the mechanism and the running system.

### The maths

#### Sleep window instead of a clock window
**KEEP** *(rubric: architecture and design)*

Right in principle, and the evidence base is narrower than the repo claims.

The reasoning is sound: the reading should come from when you actually slept, and this
device reports sleep staging while the source paper's did not. Naps are excluded on real
evidence (Whitehurst, Naji and Mednick 2018, 32 adults, polysomnography, heart rate
measurably higher in daytime naps at matched stages).

**Measured on 21 real people with real Fitbit sleep staging**, comparing the same nights
scored both ways:

| | |
|---|---|
| Night-to-night spread improved on the sleep window | 6 of 21 |
| Unchanged | 10 of 21 |
| Worsened | 5 of 21 |

So on this cohort it is **a wash**. The reason is visible in the data: only 3 of the 21 had
more than 35 percent of their sleep outside midnight-to-07:00, and the mean change for
those 3 was slightly worse. This cohort is almost entirely conventional sleepers, for whom
the clock window is already nearly right.

That does not make the decision wrong. It makes the justification specific. The project's
own subject sleeps roughly 03:00 to 11:00, and for them the measured effect was large:
night-to-night spread fell from 8 bpm (48 to 56) to 1 bpm (44 to 45). **The sleep window is
strongly justified for this user and unproven for people who sleep conventional hours.**
The documentation should say that rather than implying a general improvement.

#### The nightly value: the median, and no step filter
**KEEP, now justified by measurement** *(rubric: architecture and design)*

The thresholds are borrowed from NightSignal. I read the authors' own implementation. It
takes the **mean** of minute heart rates between 00:00 and 06:59, and **only minutes where
the step count is zero**. This system takes the median of all minutes in the window and
ignores steps.

The first draft called this a FIX and recommended adopting the step filter, on the theory
that it removes movement. **I tested it on 101 real people, scoring the same nights both
ways:**

| | Night-to-night wobble, median across people |
|---|---|
| Every minute in the window | **2.97 bpm** |
| Only minutes with zero steps | **2.97 bpm** |

Only 15 of 101 people improved. Median change: zero. **The step filter does nothing here,
and the reason is the other deviation.** NightSignal uses the mean, which a handful of moving
minutes drags upward, so it must exclude them. This system uses the median, which is already
robust to a minority of high minutes. Two deviations that looked independent are one choice
and its consequence, and together they are sound.

The recommendation to adopt the step filter is withdrawn.

#### The 180 minute coverage floor
**KEEP** *(rubric: architecture and design)*

Measured on real data: 92.4 percent of nights survive it, median 98.9 percent per person.
It discards more than half the nights for 12 of 120 people, who are presumably poor
wearers. That is the right behaviour: a reading over a fragment of a night is not
comparable to one over a whole night.

#### The baseline centre: your own median after seven nights
**KEEP** *(rubric: architecture and design)*

Correctly sourced and correctly implemented. Alavi et al. 2022: "For each individual we use
the streaming median of average overnight RHR as the baseline", and "only after seven
nights, it hits a baseline close to the baseline over three months" for over 80 percent of
subjects. Both quoted verbatim from the paper.

The fix that produced this was the most important thing the project has done. The previous
permanent blend left a person at 45 bpm needing a 6.5 bpm rise to reach YELLOW, when
infection raises overnight heart rate by a few beats. The real subject sits at 44 to 47 and
could not have been flagged at all.

#### The baseline scale: still a permanent blend
**FIX** *(rubric: architecture and design)*

The identical argument was not applied one level down. The scale, which sets the band width
and `robust_z`, is still `0.8 x your own spread + 0.2 x 8.64`, so a fifth of it is
permanently the population figure and never washes out.

Measured on a simulated subject with 28 nights of perfectly steady data: personal spread
exactly zero, scale **1.728**, which is entirely the population contribution. On the real
subject at three nights the scale is 6.048, of which most is borrowed.

This matters because `robust_z` is the unit the two extreme-heart-rate safety rules are
written in. A rule that fires above z = 6 needs a residual of about 10 bpm at a scale of
1.728. Whether that is the right trigger is unknowable while the scale is partly somebody
else's.

#### The population prior, 62.75 bpm with a spread of 8.64
**FIX** *(rubric: safety and governance, disclosure)*

The numbers are exactly right. I fetched the paper: "Participants had an average RHR of
62.75 bpm (SD = 8.64 bpm)", n = 525.

The problem is who those people are. Bloomfield et al. 2024 studied **first-year university
students aged 18 to 24, during their first semester**. `constants.py` and the dashboard
both describe it as "a 2024 study of 525 adults". True, and it hides the only thing about
the cohort that matters. A separate study of 92,457 wearable users (Quer et al. 2020, PLOS
One) found individual normal resting heart rates differing from one another by nearly 70
beats per minute.

The centre no longer uses this figure after seven nights, so the exposure is smaller than
it was. The scale still does, permanently.

#### Detection thresholds, 3.0 and 4.0 bpm
**KEEP** *(rubric: architecture and design; evaluation)*

Verified verbatim against the paper and against the authors' own code, which literally
contains `yellow_threshold = 3` and `red_threshold = 4`. The justification for 3 is
quoted: "the median of fluctuation of medians of average RHR overnight over three months
was only three bpm".

Now also validated empirically, above.

#### The persistence rule
**FIX, and this is now the main lever on the detector** *(rubric: evaluation and results)*

NightSignal raises a red alert when the reading is at or above baseline + 4 on **two
consecutive nights**. This system flags when two consecutive nights are raised and **at least
one** is RED, so RED followed by YELLOW also fires. That is strictly looser, and nothing says
so.

I swept both threshold families over the cohort. Sensitivity is measured in the seven days
before symptom onset; the alert rate is investigations opened per person-week on the 76
people with no illness label.

| Yellow | Red | Rule | Sensitivity | Alerts per person-week | One every |
|---|---|---|---|---|---|
| 3 | 4 | at least one RED | **56.7%** | 0.293 | 3.4 weeks |
| 3 | 4 | **both RED** | 50.0% | **0.204** | **4.9 weeks** |
| 4 | 5 | at least one RED | 50.0% | 0.201 | 5.0 weeks |
| 5 | 6 | at least one RED | 46.7% | 0.147 | 6.8 weeks |
| 6 | 7 | at least one RED | 33.3% | 0.098 | 10.2 weeks |

Today's setting buys 6.7 points of sensitivity for **44 percent more investigations**. Two
other settings reach 50 percent at about 0.20 per week, and nothing reaches 56.7 percent
cheaply. Given that every investigation opened on a healthy person is a chance to interrupt
them for nothing, the published rule is the better trade.

**I also tested whether a personal threshold would do better**, using `robust_z` instead of
beats, since the system already computes it and never uses it to decide anything. **It does
not.** At every matched alert rate the fixed threshold in beats is equal or better, because
dividing by a person's own wobble shrinks a noisy person's real signal along with their
noise. At one investigation every 5 weeks: 46.7 percent for the fixed threshold against 46.7
percent for the personal one, at a lower alert rate for the fixed one.

So the 3.0 and 4.0 bpm thresholds are confirmed and should stay. The persistence rule should
be tightened to the published one.

#### Explained variance: subtracting a recorded workout
**KEEP** *(rubric: architecture and design)*

`EXERCISE_EFFECT_BPM = {"0-2h": 2.91, "2-4h": 1.87, "4-6h": 1.58}`. I read the paper's
Table 4 out of the PDF in this repository. The incremental contrasts transcribed in
`constants.py` match the paper **exactly, to two decimal places, all 28 of them**. The
sums that produce the stored values are arithmetically correct.

One documentation nit: `constants.py` says "2.91 and 1.58 are exactly the paper's figures".
They are sums the repo computed from the paper's figures, not printed values. The
derivation is sound; the sentence overstates it.

The direction of the rounding rule (take the smallest figure the band supports) is right
and well argued: this quantity is subtracted from the elevation, so overstating it hides
illness.

#### The robust z-score
**KEEP** *(rubric: architecture and design)*

Median absolute deviation scaled by 1.4826 to be comparable with a standard deviation, with
a floor of 1.5 because MAD is exactly zero on whole-number heart rates. That floor is
necessary and correctly reasoned: without it every night is an infinite deviation. The
choice of a robust measure over a standard deviation is right for data with occasional
extreme nights.

Its only consumers today are the display and two safety rules that never run.

### The knowledge tables

#### infection `effect_mean_bpm = 1.60`
**KEEP the number. FIX the citation.** *(rubric: safety and governance)*

**This section reverses the first draft, and the reversal is the most important correction
in this document.**

**What I said first.** That 1.60 bpm was far too small, that it was incoherent with the 3
and 4 bpm thresholds, and that it was the reason the system cannot conclude illness. I
called it the most consequential error in the project.

**What I did about it.** I measured the infection effect directly, on the 30 labelled COVID
cases, using this system's own baseline code so the answer comes out in the same units the
detector works in. Taking the highest night in a window is biased upward by construction, so
the illness windows are compared against matched windows in people with no illness label:

| Highest night above the person's own baseline, 7 night window | median |
|---|---|
| Healthy people, random 7 night windows (46 windows) | **5.00 bpm** |
| The 7 nights before symptom onset (23 cases) | **6.00 bpm** |
| **What the infection adds** | **+1.0 bpm** |

Repeated counting only minutes where the person was still, the difference is **+1.5 bpm**.

**`causes.yaml` says 1.60 bpm. The measurement says 1.0 to 1.5 bpm. The number is right,
and I was wrong.**

**Why I was wrong, since the reasoning error is worth recording.** I argued that a cause
smaller than the detection threshold could not explain a flagged night, so the cause must be
bigger. The other explanation is the correct one: **a flagged night is usually noise, not
infection.** Measured on the same data, a healthy person's highest night in any seven night
stretch sits about 5 bpm above their own baseline, and 67 percent of healthy seven night
windows contain a night at or above the 3 bpm threshold. The signal really is buried under
the noise, exactly as `causes.yaml` says in its own header, and the belief model is behaving
correctly when it says infection is unlikely on a typical flagged night.

**What is still wrong.**

**The citation points at the wrong paper.** `docs/CORPUS-VERIFICATION.md` lists this figure
under "Confirmed, verbatim" and credits "average peak increases relative to baseline of 1.8%
for females and 3.4% for males" to Mishra et al. 2020. I fetched that paper and searched it.
**Those percentages are not in it.** They are from Natarajan, Su and Heneghan 2022,
*Frontiers in Physiology* 13:898251, which `causes.yaml` does not cite at all. The document
written to prove the citations were checked misattributes the most important number in the
system.

**The derivation mixes cohorts.** A percentage from 7,200 Fitbit users is multiplied by
62.75 bpm, the mean of 525 first-year university students from a different study. It happens
to land in the right place, which is luck rather than method. And because it is a proportion
it scales with the person: on this project's own subject, whose nights sit at 44 to 47 bpm,
the same percentages give 0.8 to 1.5 bpm.

**One number is doing the work of two.** The measurement shows two clearly different
regimes. Before symptoms the effect is about 1 to 1.5 bpm. At and just after symptom onset
it is much larger: comparing 15 night windows, the illness median is 11.0 bpm against a
control median of 7.0, and the day-by-day median curve peaks at **+6.00 bpm on the day after
onset**. The model carries one size with a shape on top, and the shape peaks at 1.0, so the
model's maximum is 1.60 on any night. That captures the pre-symptomatic regime and
understates the symptomatic one by roughly four times.

**What this does not change.** The live run still shows infection sitting fourth:

```
p(infection)         0.0756
p(stress)            0.8147
p(alcohol)           0.5536
p(sleep_restriction) 0.4813
```

`BLOCKERS.md` records this as "LIKELY_ILLNESS is unreachable under the authored knowledge
tables" and asks which of three numbers is wrong. **After the measurement, the answer is
none of them.** The infection effect is right, the thresholds are right, and the ordering is
the honest consequence of a signal that is genuinely smaller than the noise. The fix is not a
different number. It is a stricter alert rule so that fewer noise nights reach the belief
model at all, which is measured in the next section.

#### exertion `effect_mean_bpm = 4.14`
**FIX** *(rubric: safety and governance)*

The same number was corrected in `constants.py` on 4 September 2026 with the reasoning
"4.14 appears nowhere" in Leota et al. 2025. I confirmed that against the PDF: the paper's
high-strain-versus-none values bracket it at 2.91 (2 hours before sleep) and 5.59 (at sleep
onset), and 4.14 is neither.

`causes.yaml` still carries `effect_mean_bpm: 4.14` with the derivation "High-strain
session ending 0 to 2 hours before sleep, +4.14 bpm". One file was corrected and its twin
was not.

This is not cosmetic. Exertion at 4.14 bpm is the second largest effect in the table and
competes directly with infection to explain a raised night. Correcting it to 2.91 would
**raise** p(infection) on every elevation. The narrow exception granted on 4 September
covers exactly this case: the published source can be quoted saying something different.

#### alcohol `effect_mean_bpm = 2.60`
**FIX** *(rubric: architecture and design)*

The citation is exact. I fetched the paper: "consuming one drink more than personal
average, compared with one less, was associated with an increase in RHR by 2.8 bpm (99.9%
CI: 2.7, 2.9) in females and 2.4 bpm (99.9% CI: 2.3, 2.4) in males", n = 20,968, 5,109,185
person-days. Base rate 29.9 percent of person-days confirmed.

Two problems with how it is used.

The quoted contrast is between **one drink above** the person's average and **one below**,
which is a two-drink span, not one drink. Using 2.8 as the effect of "alcohol is present"
is not what the paper measured.

And the paper is explicitly dose dependent: "Increases in alcohol intake were associated
with dose-dependent increases in RHR". The probe offers "1 to 2", "3 to 4", "5 or more".
The model has one alcohol switch, so all three answers produce the same effect size. The
dose is collected and thrown away.

#### luteal `effect_mean_bpm = 3.91`
**KEEP** *(rubric: safety and governance)*

Exactly right, and the September correction was correct. Fetched from the paper: follicular
mean 56.56 bpm, late luteal mean 60.47 bpm, difference 3.91. Wrist skin temperature 33.87
to 34.32 = +0.45 C, respiratory rate 16.57 to 17.04 = +0.47/min. n = 193 participants, 708
analysed cycles. Every figure checks out.

#### vaccination, recovery tail, sleep restriction base rate
**KEEP**

Quer et al. 2022 (n = 5,674): peak day 2, back to baseline by day 6, stronger after the
second dose. Radin et al. 2021: 234 positive against 641 symptomatic negative, resting
heart rate not back to baseline until 79 days, 32 participants (13.7 percent) more than 5
bpm above for over 133 days, sleep at 24 days, steps at 32. Liu et al. 2016 supports 34.8
percent. All confirmed.

#### travel, sleep restriction effect size, unexplained spread
**UNEVIDENCED**, and correctly declared as such in the file.

`causes.yaml` states it plainly: no wearable study quantifying a travel effect on nocturnal
resting heart rate was found; the sleep restriction effect size is assumed and set
deliberately small; the unexplained spread is a leak term by construction. That honesty is
genuine and rare.

**The gap is disclosure.** The rule this project sets for itself is that an unevidenced
choice is stated in the docs **and on the dashboard**. These are in the docs. The
dashboard shows the ranked causes with probabilities and does not distinguish a cause whose
effect size came from a study of 14,689 people from one that was assumed.

#### The nine probe likelihood tables, about thirty numbers
**UNEVIDENCED** *(rubric: safety and governance)*

`probes.yaml` is the most honest file in the repository: "Almost every likelihood here is
ASSUMED. No published measurement exists of how accurately a person reports drinking,
stress or sleep to an app when prompted the next morning... A model asked to cite these
will search, find nothing, and produce a confident number anyway."

That is exactly right and I could find nothing either. These numbers convert your answer
into a change in belief, which is the step the whole EVSI argument depends on. They are set
conservatively, which biases toward asking less rather than more, which is the safe
direction.

Same disclosure gap: the differential panel quotes them to you as "That answer is expected
in 25% of cases where this is contributing, against 3% where it is not", with the
provenance in small print, on a screen otherwise full of cited figures.

### The deterministic safety logic

#### The tier A / tier B / tier C structure
**KEEP** *(rubric: safety and governance)*

Fixed phrase rules, plus a model second opinion, combined by set union in code so the model
can add a flag and never remove one. A model failure falls back to the deterministic result
rather than blocking. This is the right shape, and it is enforced where it should be: in
code, not in a prompt.

The negation guard is deliberately simple and correctly scoped: "no fever, but chest pain"
denies the fever and escalates the chest pain, because the guard stops at a comma and at
"but". Verified by reading and by test.

#### The Marburg Heart Score
**KEEP the design. FIX the age gate.** *(rubric: safety and governance; prototype safety response)*

Every item, the cut-off, and the performance figures check out against the paper:
sensitivity 87.1 percent (95% CI 79.9 to 94.2), specificity 80.8 percent (77.6 to 83.9),
AUC 0.87 derivation and 0.90 validation, 1,199 consecutive patients aged 35 and over across
74 German general practices.

The division of labour, model elicits and rule decides, is the best single idea in the
system. Two live runs, same rule, opposite outcomes, both correct. The extraction stores
each item with the person's own words beside it, including the inverted palpation item
stored as the literal answer.

**But the rule was validated only in people aged 35 and over, the code checks for that, and
`age_years` is populated by nothing.** In a live run the person said "I am 24 and male",
the extractor correctly stored that as zero points for the age item, and the system then
applied a rule outside its validated range anyway, scored 3 of 5, routed to urgent, and
told them it was using "a 2010 study of 1,199 people with chest pain". The three points
came from items that are all common in a healthy young adult with a muscular strain. The
system already had the age. It threw it away.

#### The blood oxygen rule
**FIX** *(rubric: safety and governance)*

The reasoning is excellent and the code is well written: require ten readings inside the
sleep window, use the median not the minimum because this sensor produces movement dips
(the real device gave an 80 percent followed by a 92 percent sixty-six seconds later), and
never render a normal reading as an all-clear because these sensors read high on darker
skin.

It has never run. `check_overnight_oxygen` is called by nothing, and tested by nothing.

Two evidence problems as well. The threshold is attributed to "WHO guidance as reported in
the wearable SpO2 literature". I could not find a WHO source for "above 94 percent can be
cared for at home, below 93 percent warrants medical attention". The 94 and 92 action
thresholds are **NHS England and British Thoracic Society** guidance, as popularised in the
BMJ remote-monitoring literature. The numbers are standard; the attribution is not
supported.

And those thresholds are for **people already known to have COVID-19, being monitored at
home**. Applying a triage threshold designed for a known-positive population to a healthy
person's overnight readings changes its meaning: at low prevalence the same cut-off
produces mostly false positives.

The skin pigmentation caution is also stated more strongly than its source. The review is
real (23 studies, 59,684 participants) and its own conclusion is that the overestimation
"may not be clinically relevant". Erring toward caution is the right direction; the docs
should not imply the paper says more than it does.

#### The two extreme heart rate rules
**FIX** *(rubric: safety and governance)*

Never receive `robust_z`, so never fire. Confirmed by coverage.

#### The escalation wording
**FIX** *(rubric: safety and governance)*

Two problems.

`red_flags.yaml` lists "nothing to worry about" among the phrases the system must never
say, and the code's false-reassurance filter lists it too. The dashboard's headline for a
benign investigation is **"Probably nothing to worry about"**. The filter runs on model
output, not on the interface's own hard-coded strings.

And an ESCALATED disposition produces the recommended action **"monitor"**, because the
mapping is `"rest" if LIKELY_ILLNESS else "monitor"`. The only branch that sets
`seek_urgent_care` is the human review escalate decision, which is auto-approved past.

### The machine learning

#### Chronos forecast
**DROP** *(rubric: architecture and design; you lose a talking point, and nothing else)*

It costs 182 MB of model weights, a PyTorch dependency, and a per-night inference. It
changes no decision the system makes, by design. It produces one advisory paragraph on one
screen.

**The first draft justified this with a paper, and the justification was too weak.** I cited
Alavi et al. 2022, where a forecast-style detector scored 44 percent against 78 for plain
baseline deviation. But that paper compared a forecast used **instead of** a detector. This
system uses one **alongside** a detector, which is a different claim. Stretching a paper past
its design is the exact fault I criticise elsewhere in this document, so I tested the real
question instead, on 7,295 real nights with a forecast computed for every one.

| | Separates illness nights from ordinary nights |
|---|---|
| The plain baseline residual, which the detector already has | **AUC 0.629** |
| The Chronos forecast residual | **AUC 0.586** |

An AUC of 0.5 is no separation at all. **The forecast separates illness worse than the number
the system already has.**

Asked the more generous question, whether it catches anything the detector misses, across 30
labelled infections: at the loosest setting it found **one** case the detector missed, and at
tighter settings **none**.

It is not simply a duplicate. The two correlate at 0.73, so it is measuring something
partly different. What it measures is just less useful.

**So: DROP, on evidence from this system's own data rather than from someone else's paper.**
And for a coursework report this is a much stronger section than keeping it would have been:
you tested whether a time series foundation model added detection signal over a simple
personal baseline, on 7,295 nights of real labelled data, found that it did not, and removed
it. That is a justified model choice with evidence behind it. "We included a foundation
model" is not.

### The Bayesian belief

#### Exact enumeration over 4,096 states, in log space
**KEEP** *(rubric: architecture and design)*

This is the best engineering decision in the project. Twelve binary causes means 4,096
combinations, which is small enough to enumerate exactly in microseconds, so there is no
approximation and no sampling anywhere. Log space is mandatory rather than clever: products
of thousands of densities underflow to zero within days, and the failure mode is a uniform
posterior that looks fine.

Modelling causes as co-occurring rather than mutually exclusive is right. You can have a
drink and an infection.

#### The temporal profiles
**KEEP**

The profiles are what actually separate the causes. Alcohol contributes on night one and
stops; infection rises then fades; the luteal plateau lasts twelve days. `causes.yaml`
states the consequence correctly: a single-night model cannot separate alcohol from early
infection at all.

#### The differential shown to the person
**FIX** *(rubric: architecture and design; prototype observable workflow)*

The twelve numbers are independent marginal probabilities that each cause is present. They
do not sum to one and they do not compete. A cause that is common and small scores high on
any raised night, because something must explain the rise and several small things can.

Presented as a ranked bar chart with the heading "Cause Differential", it reads as a
differential diagnosis, and it is not one. Measured on a real closed episode:

- disposition: **LIKELY_ILLNESS**
- the chart immediately underneath: **stress 0.9228**, infection 0.7774
- the reason attached to the top entry: "Nothing gathered in this episode speaks to this
  cause either way. Its position reflects its base rate of 35.0% of nights alone."
- the audit page, in plain English: "most likely **stress** at 93%, chance of illness 78%"

A person reads "we think you are ill" directly above "most likely cause: stress, on no
evidence". This is not a rendering bug; it is a mismatch between what the model computes
and what the panel claims to show.

#### Cycle applicability
**FIX or DROP** *(rubric: architecture and design)*

Three-state cycle applicability was a correct and important fix: defaulting an unasked
subject to "menstruates" let the largest benign effect in the table explain away exactly
the elevations the system exists to investigate.

But **no production caller ever passes the answer back in.** Every call site invokes
`update_belief` without the context, so `luteal_applicable` is always unknown, the base
rate stays clamped at 1e-12, and the cause is inert forever. Confirmed on a live run:
luteal 0.0 throughout. `probe_cycle` can be asked, costs 0.4 of an interruption, and its
answer is arithmetically inert. The same call path means the recent-illness boost for
`recovery_tail` never fires either.

For a single male user, inert luteal is the correct behaviour by accident. The mechanism to
make it correct on purpose does not exist.

#### `one_time: true`
**FIX**

`probes.yaml` marks `probe_cycle` and `probe_medication` one-time and justifies their low
interruption cost of 0.4 with "asked once and then becomes a modelled covariate". The
loader constructs its model field by field and never reads `one_time`; the field is dropped
silently. `already_asked_probe_ids` is per episode. Nothing makes them once.

#### Two copies of the residual likelihood
**SIMPLIFY**

`compute_residual_loglik` exists in both `belief/likelihood.py` and `belief/inference.py`.
They differ: one clamps the profile index at both ends, the other only at the top. Coverage
over a production run shows the `likelihood.py` copy and the whole of `run_exact_inference`
never execute. Delete the unreachable pair.

### The EVSI policy

#### The policy itself
**KEEP** *(rubric: architecture and design; evaluation)*

This is the intellectual contribution of the project and it works. Measured live: belief
0.0756, inside the quiet band, the policy asked `probe_symptoms` with EVSI **0.3935**
against a cost of 1.0, having scored and rejected eight alternatives. The answer moved
p(infection) from 0.0756 to 0.4051. Then it stopped, because every remaining probe fell
below its cost. **The weekly budget was not the binding constraint. The arithmetic was.**

The decision threshold is derived rather than chosen: from a miss costing nine times a
false alarm, the threshold is 1/(1+9) = 0.10, which coincides with Pauker and Kassirer
(1980). That is the right way round.

The quiet band is a real property, not a story. Asking is worth it only between roughly
p = 0.06 and p = 0.28, because outside that range no answer changes what you do.

#### The interruption budget of two per week
**SIMPLIFY** *(rubric: safety and governance, alert fatigue)*

The citation is real and I verified the sentence: "Of all patient monitoring alarms, 72% to
99% are either technically false... or clinically irrelevant". It is a systematic review of
**intensive care unit bedside monitors**. Extending that to a phone notification is a large
jump the file does not acknowledge.

More to the point, the cohort measurement above shows the budget is not doing anything. The
detector opens an investigation into a healthy person about **once every 4.9 weeks** (3.6
as measured here, before item 8 tightened the alert rule to the published one), and the
policy asks at most one question per episode. A limit of two per week is never
approached. It is machinery guarding a door nothing walks through.

#### `POLICY_COST_PER_INTERRUPT = 0.15`
**KEEP**, and note what it costs.

Genuinely swept, and the sweep is in the file. The project's own evaluation shows the price:

| Policy | Accuracy | Questions per episode |
|---|---|---|
| EVSI at 0.15 | 0.675 | 0.40 |
| Always ask | **0.825** | 2.00 |
| Never ask | 0.500 | 0.00 |

Always-ask beats EVSI by 25 accuracy points. The policy trades a quarter of the available
accuracy for a five-fold reduction in questions. Given the measured alert rate, that trade
looks less obviously right than it did: you are protecting a person from about one extra
question every three weeks.

#### `CONVERSATION_MAX_TURNS = 10`
**FIX or DROP** *(rubric: safety and governance, stop conditions)*

Correctly cited. AMIE: "both AMIE and PCPs were able to acquire the information necessary
for formulating an accurate differential in the early stages (first ten turns)", and
accuracy plateaued within ten turns.

The code computes whether you are at the limit, attaches it to the reply, and **nothing
reads it**. No refusal, no warning, no stop. Either enforce it or delete the constant and
the citation, because a stop condition that does not stop anything is worse than no stop
condition: it appears in the report as a control that exists.

#### `DEPTH_BUDGET_PER_EPISODE = 5`, `MAX_TOOL_CALLS_PER_EPISODE = 25`, `EPISODE_MAX_STEPS = 40`
**KEEP**

Real, enforced, and doing their job. The tool call counter charges for refused calls too,
which closes the loop where a model that keeps requesting an unregistered tool spins
forever.

#### `MEASURE_MIN_LEADING_PROBABILITY = 0.5`, `TRIAGE_MAX_TURNS_BEFORE_ESCALATE = 3`
**UNEVIDENCED**, and correctly declared in `constants.py` as such. Both are disclosed in
`docs/DISCLOSURES.md`.

### The agent

#### Is it genuinely agentic?
**KEEP.** Yes, on the definition that matters.

It selects tools based on what earlier tools returned, and its loop re-enters after new
evidence arrives. Measured: on the step immediately after the answer "fever", the model
called `retrieve_clinical_evidence` for the first time in the episode, with a query it
chose. That is the model following up on what it just learned, which a chatbot with extra
steps does not do.

The autonomy is narrow and deliberately so: it cannot decide to interrupt you, cannot write
to your record, cannot choose a disposition, and cannot lower urgency. The right
description is a **bounded investigator inside a deterministic frame**, and for a health
tool that is better than a free agent.

#### LangGraph interrupt and resume with a SQLite checkpointer
**KEEP** *(rubric: architecture, state across asynchronous waits)*

The hardest engineering in the project and it works. An investigation parks on a question,
the process can exit, and days later the answer resumes the graph exactly where it stopped.
The requirement that everything before an `interrupt()` be idempotent is understood and
respected in most places.

One consequence not handled: the ask node calls the model to word the question **before**
the interrupt, so a resume re-runs that call and overwrites the stored question with newly
generated text at temperature 0.3. The record can end up showing a question the person
never saw.

#### The closed tool registry
**KEEP** *(rubric: safety and governance, over-permissioning)*

Fixed list, refusal by name, refusals audited, model-supplied subject ids stripped and
counted as expansion attempts, date ranges clamped to 90 days and to not-in-the-future,
results cached per episode. This is genuinely good and it is the part most directly
transferable to other projects.

#### `get_data_quality`
**FIX** *(rubric: safety and governance)*

Returns three invented constants on every call for every person on every night:
`coverage_ratio 0.95, missing_hours 0.35, dropped_samples 0`. Confirmed in the audit log of
a live run, on nights whose real coverage was 341 to 362 minutes. It ignores both the
database and its own arguments.

This is a health system fabricating data and handing it to its own reasoning layer, and it
is the tool that would otherwise inform judgements about sensor artefact. The real numbers
exist two function calls away and are already used by the belief model, so the arithmetic
and the agent are told different things about the same night.

#### `get_local_disease_activity`
**DROP** *(rubric: architecture, tool integrations)*

Fetches a Singapore government endpoint with no query parameters and returns
`{"status": "active", "bytes": <length>}`. It never parses dengue clusters, never checks
whether the subject is inside one, and never queries the air quality endpoint that is also
allow-listed. `sources.yaml` claims "A subject inside an active cluster materially raises
the dengue prior, and no shipped product does this". Nothing raises any prior, and there is
no dengue cause in the model to raise.

Either implement it properly, which means adding a cause and a likelihood and is therefore
a clinical decision, or delete it and delete the claim. Shipping a tool that returns a byte
count under a docstring about outbreak surveillance is worse than not having it.

#### The MEASURE limb
**DROP** *(rubric: architecture)*

Three independent breaks, any one of which is fatal:

1. Nothing anywhere writes a row to the `measurements` table. Confirmed:
   `grep -rn "INTO measurements" src tests` returns nothing.
2. `AWAITING_MEASUREMENT` is never set, so the request cannot appear in the dashboard.
3. The resume logic returns `{"declined": True}` for a measurement regardless of what the
   database says.

So the policy can select it, a notification goes out, and the answer can never come back.
`compute_measurement_logfactor` is unreachable.

Fixing it is three small changes. But ask first whether it earns them: it fires only when
sensor artefact leads the differential at 0.5 or more, which is an unevidenced threshold,
and it asks a person to count their pulse for 30 seconds and double it, which is a
measurement with its own considerable error. The simpler honest behaviour is to tell the
person the night could not be judged.

#### The human review checkpoint
**FIX** *(rubric: safety and governance, mandatory human-in-the-loop)*

The node exists, the interrupt fires, the four decisions are implemented, and the API
endpoint is there. And a background job answers it "approve" fifteen minutes later, because
`_resume_value` handles a question and a measurement and falls through to
`{"decision": "approve"}` for everything else. `AWAITING_HUMAN_REVIEW` is never set, so it
could not have been surfaced to a human anyway.

This is the rubric's mandatory human-in-the-loop checkpoint. As shipped, the system
approves its own clinical output on the human's behalf and records that a human did it.

#### The critique node
**KEEP**

Subtractive only, and enforced: if the model returns longer text than it was given, the
longer text is discarded. That is the right way to constrain a second pass.

### Retrieval and the corpus

#### Hybrid BM25 plus dense embeddings with reciprocal rank fusion
**KEEP** *(rubric: safety and governance, RAG grounding)*

The right choice for this corpus, which contains both plain-English consumer text and
tables of clinical figures. Keyword search misses paraphrase; embeddings miss exact terms
and numbers. RRF combines them using only rank, so two incomparable scoring schemes merge
without tuning. Embeddings cached to disk by content digest: 343 seconds cold, 3.0 seconds
warm.

#### Reranking
**DROP the claim.** There is none. `grep -rni "rerank|cross.encoder"` over `src` and the
contract returns nothing. RRF is fusion, not reranking. Any description of a reranking
stage describes something that does not exist.

Adding one is the single highest-value retrieval improvement available, because the
relevance problem below is exactly what rerankers fix.

#### Retrieval relevance
**FIX** *(rubric: safety and governance)*

Poor, and visible to the user. For a fever episode, four of the five passages on the
Evidence tab were about **meningism** (stiff neck), and the top-ranked "evidence" was the
list of answer options for the symptom question. In a chest pain conversation the single
cited source under an urgent escalation was "How to Prevent Heart Disease".

The grounding check guarantees a sentence came from a passage. It guarantees nothing about
whether the passage is relevant, and the interface presents retrieved passages as
"Knowledge Citations and Evidence".

#### The generated layers leak the internals
**FIX**

Because layers 2 and 3 are generated from YAML, the passages shown to a lay reader include
the raw phrase-match lists: "Any of: 'stiff neck', 'neck stiffness', 'can't touch chin to
chest'", and the entire tier B table with its trigger phrases and persistence thresholds.
That is the system's internal keyword list presented as clinical evidence, and it publishes
exactly which words cause an escalation.

#### The missing layers
**FIX the claim, not necessarily the corpus** *(rubric: discussion and limits)*

`sources.yaml` describes four layers. StatPearls, the actual clinical-reference layer, has
never been fetched; what the corpus calls layer 2 is three passages generated from
`constants.py`. The Singapore care-pathway layer is the nine passages already in
`red_flags.yaml`, not the curated national guidance the design describes. Both are recorded
in `BLOCKERS.md`, and `sources.yaml` still describes what is not there.

#### Injection scanning
**KEEP**

Every retrieved passage is scanned before the model sees it, and detection **contains
rather than drops**: the passage flows through marked, with the matched pattern recorded.
That is the right call, because silently discarding evidence is its own failure mode and
the audit needs to show what was seen. It now runs in production, which it did not for most
of the project's life.

### Grounding and claim-to-source enforcement

#### The verbatim containment test
**KEEP** *(rubric: safety and governance, hallucination mitigation)*

The best safety idea in the system. The model must supply a span of text it says supports
each claim, and plain code checks whether that span appears word for word in a retrieved
passage after normalising whitespace and case. Not similar to. Contained in. The citation
attached is the passage the span was **actually found in**, decided by code, not by
whichever source the model named.

Verified working on a live Telegram message: the model wrote "usually above 98.6 °F (37
°C)", the MedlinePlus passage contains "it is usually around 98.6 °F (37 °C)", the span
matched, the claim stood, and the citation is correct.

#### The escalation criteria exemption
**FIX. Highest priority.** Described at the top of this document.

#### `stripped_claims` hard-coded empty
**FIX** *(rubric: safety and governance, audit)*

`get_episode` sets the list to `[]` and never fills it. The Evidence tab therefore always
shows a green tick and "No claims were stripped", followed by "all generated statements
were successfully grounded", whatever actually happened.

### The conversation

#### The two-call design
**KEEP** *(rubric: architecture, prompt as specification)*

Asked to converse and to extract rule answers in one response, the model conversed: it
asked the Marburg questions correctly and recorded none of the answers, so a person
describing chest pain was left with no urgency at all. Splitting extraction into its own
zero-temperature pass fixed it, and the extraction quality in live runs is genuinely good.

#### Monotone urgency
**KEEP the rule. FIX the expiry.**

Urgency read back from the stored transcript rather than held in memory, so a restart
cannot lose an escalation. Correct.

But it is the maximum over the entire transcript with no time limit. A "see a doctor today"
banner from a conversation days ago is still at the top of the Today page, undated, with no
way to resolve it. Training a person to ignore a persistent red banner is precisely the
alarm fatigue this project cites in its own constants.

#### The amber "not from a cited source" label
**UNEVIDENCED as a guarantee**, and correctly recorded as such in `BLOCKERS.md`.

It depends on the model classifying its own sentences, which is the same judgement the
model is making. On the dashboard, in a real transcript, the model wrote **"that's
reassuring"** and "which suggests it might be muscular" directly into the reply with no
warning, while on an adjacent turn it correctly moved a similar sentence into the amber
panel. The label is a floor on labelling, not a ceiling on unlabelled model content.

Note also that "that's reassuring" is not on the never-say list, and arguably should be.

#### Offering capabilities it does not have
**FIX**

In a real Telegram message sent during this review: "Would you like me to check your current
temperature readings from your watch?" The watch does not measure temperature and never
has. The same message showed that sentence twice, because the model put it in both the
reply and the question field and the code appends the question to the reply.

#### `report_symptoms`, a second escalation path
**SIMPLIFY**

A parallel implementation of "check the floor, open an episode, close it as ESCALATED,
notify". It is reachable only from the CLI and the demo harness; the dashboard and Telegram
both route free text to the conversation engine instead. So "I have chest pain" behaves
differently depending on which surface you type it into, and the CLI path is the one that
creates episodes. Five identical closed ESCALATED episodes in the live database, same dates,
step count zero, all shown separately on History, came from this path.

### Interfaces

#### The HTTP boundary
**KEEP** *(rubric: architecture)*

31 endpoints, generated docs, a test asserting no screen imports the service layer, and
`/config` enumerating every public constant from the module so the numbers on screen cannot
drift from the code. Bound to localhost and unauthenticated on purpose, with the reasoning
written down. Correct for a single-user tool, and it makes the front end genuinely
replaceable.

#### The execution trace
**FIX** *(rubric: prototype demo, observable workflow)*

Reports **all nine stages as SKIPPED on every episode**, with invented reasons: "Ask probe
not selected by EVSI optimizer" on an episode whose own summary says one question was
asked, and "Human review checkpoint bypassed (direct auto-approval)".

The cause is structural. The panel matches stage names against `audit_events.operation`,
and that column is a fixed list of ten values (`ingest`, `nightly`, `plan`, `retrieval`,
`execute_tool`, `invoke_agent`, `chat`, `notify`, `human_decision`, `settings`) that
contains no stage name. No audit row can ever match, so nothing can ever be marked as
having run. `stage.detail_json` is always empty, so the tool-call expander never renders
either.

The belief evolution chart immediately below it shows two real belief steps and the
probability moving 0.2954 to 0.7774, so the page contradicts itself. This is the rubric's
"observable workflow: visible planning steps, state changes, and tool calls", and it is the
single most visible defect in the product.

#### The Today page
**FIX**

Three factual errors in one expander, on the screen a person reads daily:

- "Your watch was in contact for 362 minutes **between midnight and 7am**" on a night the
  database records as measured over recorded sleep.
- "Your **lowest sustained rate** between midnight and 7am" when the value is the median.
- "after subtracting what a recorded workout **or short sleep** would be expected to add"
  when the code subtracts only exercise and `explained.py` says so explicitly.

The History page describes all three correctly, so the two screens disagree.

#### The audit log
**KEEP the design. FIX the padding.** *(rubric: safety and governance, audit logs)*

Hash chained, tamper evident, and the nightly narratives are the best writing in the
project: the whole chain from what was measured to what was decided, in sentences a person
can check by hand. Refusals are recorded as first-class events, which is unusual and right.

Three gaps. Notifications are never recorded even though `notify` is a permitted operation,
so the log does not show that a question reached your phone. Human decisions are never
recorded because there are none. And the "only changes are recorded" rule fails for ingest:
the recorder skips only when zero rows were written, and re-pulling the same window
rewrites the same rows, so the live log holds five consecutive entries minutes apart all
reading "9785 heart rate samples arrived". The page's own caption says a check that found
nothing new does not appear.

The latency column is always empty: the tool registry measures each call's duration and
assigns it to a discarded variable.

#### Telegram
**FIX** *(rubric: safety and governance, attribution)*

Works, and was verified live during this review: a question with buttons and two
conversation replies were delivered to a real phone.

It does not name the source of a citation. The message ends `Sources: Fever`, where "Fever"
is a MedlinePlus topic title. The dashboard has a module whose entire purpose is to render
that as "MedlinePlus, National Library of Medicine"; the Telegram formatter does not import
it. MedlinePlus is attribution-only licensed, and the passage text itself carries the
attribution line that is being dropped. This closes the open blocker.

The 900 character truncation also cuts mid-sentence, and in one real message the cut fell
inside the amber "not from a cited source" block.

## Is the project overengineered?

Yes, in three specific places, and no everywhere else.

**Overengineered:**

1. **Chronos.** 182 MB and a deep learning framework for one advisory paragraph that
   changes nothing.
2. **The interruption budget machinery.** Two counters, a gate, a citation and a settings
   control, guarding against an alert rate that is measured at one investigation per 3.6
   weeks.
3. **The MEASURE limb.** A whole graph node, a notification kind, a database table, a
   likelihood function and an API endpoint, for a path that has never completed and whose
   trigger threshold is a guess.

**Not overengineered, despite looking it:**

- The 4,096 state enumeration is *simpler* than the alternatives, not more complex. It is
  exact, it is microseconds, and it removes an entire class of approximation bug.
- The EVSI policy is about eighty lines and it demonstrably works.
- The closed tool registry, the hash chain, and the verbatim grounding test are all small,
  all enforced in code rather than in prompts, and all doing real work.
- The HTTP boundary is the right amount of structure for something that wants a different
  front end later.

**The real problem is not complexity. It is unreached code.** Three safety mechanisms, one
graph limb, one cause, one probe field and one stop condition exist, are referenced, are
tested in isolation, and never run. The project has diagnosed this pattern in itself four
times and it is still the dominant defect. A green test suite has said nothing about it
every single time.
