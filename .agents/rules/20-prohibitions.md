# Prohibitions

Hard rules. Breaking any of these is worse than leaving a task unfinished. Every one of them exists
because the failure it prevents is **silent**: the code runs, the tests pass, and the system is
wrong in a way nobody notices until it matters.

---

## 1. Tests

**Never modify, weaken, delete, rename, skip or `xfail` a test to make it pass.**

That includes all of these, which are the same act wearing different clothes:

- loosening an assertion (`assertAlmostEqual` where `assertEqual` was written)
- widening a tolerance
- adding `@pytest.mark.skip` or `@pytest.mark.xfail`
- changing an expected value in a fixture
- deleting a case from a parametrised list
- wrapping the assertion in a conditional
- catching the exception the test was meant to surface

You may **add** tests freely.

**The one narrow exception, and it is narrow.** A test can encode the defect rather than the
intent, and then "never change a test" would freeze the bug. `CLAUDE.md` rule 2 states the
exception and this is the same rule in full:

1. **Measure the real behaviour first.** Run it, print it, write the number down. Never reason
   about what it probably does.
2. **Decide whether the new behaviour is correct**, on that measurement.
3. **Then** change the expectation, with the measurement and the reason in the commit message.

Measure, then assert. Never the reverse, and never "the test is probably stale".

Worked examples from 5 September 2026, all in the git log:

- `test_zero_nights_returns_population_prior` asserted the band used the BETWEEN-person SD of
  8.64 bpm. Measured on 107 people, the within-person night-to-night scale is 3.71. The test was
  asserting a category error, and the fix was to the code with the test corrected alongside it.
- `test_episode_detail_includes_skipped_stages` asserted nine pipeline stages. The graph has
  eight; the ninth was a limb that had been deleted. The count now derives from the source list
  rather than a remembered number.
- `test_a_sensor_doubt_means_the_night_could_not_be_judged` passed from a hand-built belief state
  that `update_belief` never produces. Measured over 20 real combinations: the gate it guarded
  fired in none of them. The test now drives the real belief model.

If you cannot measure it, it is still a blocker.

## 2. Numbers

**Never write a numeric literal that affects behaviour.**

Every threshold, budget, window, temperature and floor lives in `src/wha/constants.py`. Every
clinical figure, base rate, effect size and likelihood lives in `data/knowledge/`.

If the value you need does not exist there, that is a blocker. **Do not estimate it, do not infer it
from a similar value, and do not take one from a docstring or a comment.**

The exceptions are obvious and few: array indices, `0`, `1`, `-1`, and format widths.

---

## 3. Read-only paths

Never create, edit, move or delete anything under:

```
history/            the finished build plan, briefs and proposal. ALL of it
docs/CONTRACTS.md   the frozen contract. Still binding, never edited
research/           evidence corpus
archive/            a superseded earlier generation. Not fact
```

`data/knowledge/` is not on that list. It is under change control instead, described below.

**The whole build plan moved to `history/` on 4 September 2026** and is entirely read-only.
`BLOCKERS.md` came out to the repository root, beside `STATUS.md`, because it is a live document
and nothing live should sit inside a finished plan. `PROGRESS.md` is frozen as a build log. The
two files you keep current are **`STATUS.md`** and **`BLOCKERS.md`**, both at the root.

Everything in `history/` is read-only, and is edited only when the user asks for it directly.

**`data/knowledge/` is under change control, not sealed. Widened by the user on 5 September
2026.** The original rule said these files could not be edited because a person wrote them. That
was not true: they were generated by a language model, and the header lines claiming otherwise
have been removed. What survives is the reason that actually matters, which is that a clinical
number must not move without evidence.

A clinical figure in `data/knowledge/` or `src/wha/constants.py` may be changed when, and only
when, one of these holds:

1. **The published source it cites can be quoted saying something different.**
2. **A measurement made in this repository, on real data, with the script committed**, says
   something different. `experiments/detection/cohort/` is the worked example.

Not a hunch that a number looks wrong, not a better number found elsewhere, and never the model's
own knowledge. Every change goes in `docs/KNOWLEDGE-CHANGELOG.md` with the old value, the new
value, and either the quoted source sentence or the command that reproduces the measurement. If
neither settles it, it is still a blocker.

Adding a **new** clinical figure is not covered by the exception and remains forbidden.

## 4. Contracts

`docs/CONTRACTS.md` defines every schema, model, field name, enum value, service signature and
constant. **Never** rename a field, widen a type, change an enum, alter a table, or change a
function signature.

If a task cannot be completed without changing a contract, the task or the contract is wrong. That
is a blocker, always. **The file itself is never edited by an agent**, because only the user can
amend it.

**What "blocker" means here in practice.** Four disagreements between the contract and the code
are open right now, recorded in `BLOCKERS.md` with the reasoning and the measurement behind each:

- five `FORECAST_*` constants the contract lists and the code no longer has, because the forecast
  was deleted on evidence
- a baseline scale line the contract describes and the code no longer computes
- `NightRow.rhr_window_source`, added so two screens could stop asserting that the watch recorded
  no sleep on nights when it did
- `DifferentialItem.moved`, added so a chart could draw the quantity its own panel is ordered by

Each was recorded rather than papered over, and `tests/unit/test_contracts.py` enumerates the
removed constants so the disagreement is visible rather than silent. That is the shape to copy:
**the contract wins until the user amends it, and the disagreement is written down where the next
reader will find it.**

## 5. Errors

- Never raise a bare `Exception`. Use the taxonomy in `src/wha/errors.py`.
- Never `except:` or `except Exception:` without re-raising, unless the contract names that
  behaviour explicitly.
- Never swallow an exception to keep a pipeline running.
- Never add `# type: ignore`, `# noqa`, or `Any` to silence a checker. Fix the type or record a
  blocker.

---

## 6. The model

- The LLM **never** decides whether to interrupt the human. That is `policy/`, in numpy.
- The LLM **never** produces a probability that reaches the user. Numbers come from `belief/`.
- The LLM **never** removes a red flag. It may only add one.
- The LLM **never** sends anything. `notify/` is not a tool and must not appear in any tool
  registry.
- No tool may run a shell command, execute generated code, fetch an arbitrary URL, or reach the open
  web. Live data comes only from the named endpoints in `data/knowledge/sources.yaml`.

---

## 7. Secrets

- Never log, print, format, or write to the audit log any value from a key ending `TOKEN` or `KEY`.
- Never commit `.env`.
- Never hard-code a host, bearer token, bot token or chat id, not even in a test. Tests use fixtures.
- `Settings` carries no secret fields. `SettingsPatch` uses `SecretStr` and is write-only.

---

## 8. Git

- Never `git push`, `git push --force`, `git rebase`, `git reset --hard`, or rewrite history.
- Never `--no-verify` or skip a hook.
- Never add a co-author trailer, an attribution line, or a tool name to a commit message.
- Commit only when a task says to.

---

## 9. Scope

- Do not refactor code a task did not name.
- Do not add a dependency. The list in `docs/CONTRACTS.md` section 1 is closed.
- Do not add a feature, a flag, a helper module or an abstraction "for later".
- Do not upgrade or pin a version differently from `uv.lock`.

If `uv lock` fails to resolve, record it. **Do not remove a dependency and do not drop the
`numpy>=2` floor.**

---

## 10. Writing style

No em-dashes anywhere: not in code comments, docstrings, commit messages, user-facing strings, or
anything you write into `PROGRESS.md` or `BLOCKERS.md`. Use a comma, a colon, or a full stop.
